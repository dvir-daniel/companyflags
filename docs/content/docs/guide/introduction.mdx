CompanyFlags is an open-source server for **feature flags and remote config**. It decides
what every app and backend gets: rules for everyone, % rollouts and releases, settings for any part of your product
(a region, a store, a team, a customer: you define the dimensions), with reviewed changes and a full history. Apps and
backends read it through OpenFeature.

You run it yourself: one Node.js server with a web console, and Postgres for the data.

## Who it's for

- **Teams that want flags they own**, run on their own servers and read with OpenFeature in every app and backend,
  so the code that reads flags stays standard.
- **Products whose config differs by part**: per region, store, team or customer, where a setting should follow a
  chain (a region's stores, a company's brands) unless one of them has its own.
- **Teams that need change control**: approvals in production, scheduled changes, break-glass for on call, an
  append-only history and restore.
- **Products with many devices** that don't want rules or lists of entities sent to every phone, or a bill that
  grows with every request.
- **Teams shipping AI-written code or AI features**: changes nobody read line by line go out behind a flag, to a few
  first, with a kill switch; models and prompts are config you roll out and roll back without a deploy. See
  [Flags in the age of AI](/guide/ai).
- **Teams moving from another system**, a flag tool or one built in-house, that can't switch everything on one day:
  both run side by side, and flags move one at a time.

## How it works

1. **You describe your business.** In **Settings → Dimensions** you say what config is served per: `customer`, or
   `company` › `brand`, or `region` › `chain` › `store`. Each customer, brand or store is an **entity**. This is
   optional: without dimensions, everyone gets the same settings.
2. **You set flags.** Each flag has rules for everyone ("10% of devices", "app version below 5.0"), and any entity can
   have settings of its own. An entity follows its parent's settings until it has its own. Locked rules apply to
   everyone, always.
3. **Apps and backends ask with OpenFeature.** Each reads a **service**: the flags you put in it. Apps use
   OpenFeature's own OFREP providers (web, Android, iOS) with their service's public key, and backends with their
   secret key. Or they download their entity's flags as [flagd](https://flagd.dev) JSON and decide each flag
   themselves: a backend with OpenFeature's flagd provider, a web or React Native app from a CDN file your CDN caches,
   read with OpenFeature's flagd evaluator (`flagd-core`, not a provider). Native mobile apps use OFREP. See
   [Reading flags](/reading/overview).

## What makes it different

- **Your words.** Dimensions are yours to name, and rules read in them: "Brand is Lumen", "Company is Globex".
- **Settings that follow the chain.** A brand follows its company's settings until it has its own; a company follows
  the rules for everyone. Each answer can be traced step by step in the console.
- **OpenFeature, no SDK of ours.** Apps and backends use OpenFeature's own providers (OFREP, flagd), so you can switch
  to or from CompanyFlags without touching the code that reads flags. The one exception is the CDN file: a web or
  React Native app reads it with OpenFeature's flagd evaluator and a short fetch loop of its own.
- **Privacy by construction.** Over OFREP an app gets values only. Its CDN file holds no list of entities and no
  rule about another entity, only the checks the device makes itself (app version, platform, % group): checks on
  dimensions, services and environments are settled on the server. A signed app link pins an app to its own entity,
  so it can't read another's values.
- **Change control built in.** Protected environments, approvals by someone other than the author, scheduled
  changes, break-glass for on call, an append-only history, and restore.
- **No big switch.** Import the old system's values, and apps keep reading it, through OpenFeature's Multi-Provider,
  for every flag not moved yet. Webhooks out and in keep both the same until the last one is here. See
  [Moving from another system](/guide/migration).

## What it doesn't do (yet)

CompanyFlags is before 1.0. It is tested (hundreds of tests, on embedded and real Postgres) but young. Not built yet:

- experiment statistics (name your % groups and send them to your own analytics instead);
- your own attributes beyond the built-in list ([Attributes](/reference/attributes));
- sending email: invite and password reset links are made by an admin and sent by hand; SCIM provisioning;
- secret values: don't put secrets in flag values.
